> 更新日期：2026-09-04

## 1. 项目概述

Food Master 是一个本地生活综合服务平台，覆盖外卖点餐与配送履约、到店团购券、酒店预订、娱乐门票、社区博客评论、AI 个性化咨询与后台运营治理九大业务场景（UC01–UC09）。

项目以课程原单体 Django 应用为起点，在保留页面/BFF 兼容层的前提下，将后端业务**渐进式拆分**为三个独立微服务，完成容器化、CI/CD 流水线、Kubernetes 部署、自动扩缩容与故障隔离的全链路改造，并以 114 项自动化测试、54 个微服务 API 契约覆盖和单体/微服务性能对照作为质量与验收证据。

| 维度 | 内容 |
| --- | --- |
| 业务场景 | 外卖、团购、酒店、娱乐、社区、AI 助手、运营治理 |
| 参与者 | 游客、普通用户、骑手、商家、管理员、外部 AI 服务 |
| 架构演进 | Django 单体（BFF 兼容层）→ 3 个业务微服务 + 网关 |
| 部署形态 | Docker Compose（本地）/ Kubernetes（Kind + 云集群） |

                 │       │        │       │

         │user-svc  │ │trade-svc│ │life-svc │ │  BFF(web) │
         │ 8001     │ │ 8002   │ │ 8003   │ │  8000     │

         └──────────── 同一 MySQL 8.0 实例 · 禁止跨 schema 联表 ────────┘

### 3.2 服务职责

| 服务 | 职责 | 端口 | 数据库 | 对应用例 |
| --- | --- | --- | --- | --- |
| `user-service` | 注册、登录、会话、角色与账号治理 | 8001 | `user_db` | UC01、UC09（用户治理） |
| `trade-service` | 外卖下单 / 购物车 / 团购券 / 配送履约 / 评价、商家菜品供给 | 8002 | `trade_db` | UC02、UC03、UC06（美食） |

## 4. 微服务拆分设计

### 4.1 拆分原则

1. **user-service 单独拆**：账号是横切基础能力，被所有业务依赖，独立后认证、风控、账号治理可单独演进。
2. **trade-service 是核心、状态机最复杂**：外卖订单 `pos 0→5` 需用户/商家/骑手三方协作，一致性要求最高，应独立以便高并发扩容。把 `Food` 与 `Order` 放在同一服务，销量统计 `sync_food_sales` 即为同服务内事务，无需跨服务事件。
3. **lifestyle-service 合并酒店 + 娱乐 + 社区**：三者都是「到店消费」模式（下单 → 到店 → 评价，无配送状态机），流量分散、复杂度低，合并不增加耦合反而降低运维成本。

### 4.2 数据表归属（11 张表）

| 表 | 归属服务 | 跨服务外键处置 |
| --- | --- | --- |
| `User` | user-service | — |
| `Food` / `Order` / `GroupBuyCoupon` / `Temp` | trade-service | 跨服务外键降级为裸 `user_id` / `merchant_id` |
| `Hotel` / `HotelOrder` / `Play` / `PlayOrder` / `Blog` / `Comment` | lifestyle-service | 同左 |

**规则**：跨服务外键一律降级为「裸 ID」，需要详情时调对方服务接口解析；同服务内保留真实外键与联表。

### 4.3 跨服务调用与失败处理

| 场景 | 方式 | 失败处理 |
| --- | --- | --- |
| 下单/评价前校验身份、判断角色 | **JWT 声明携带 `user_id` + `usertype`**，服务本地解析 | JWT 无效/过期 → 401；user-service 宕机不影响已有合法 token |
| 列表页显示用户名 | 调 user-service `/internal/users?ids=` 批量查 | 失败 → 显示「匿名用户」占位，不阻断主流程 |
| 个人中心/管理后台聚合 | BFF **并发**调用三服务 | 单点超时 → 返回该块空数据 + 提示，不整体 500 |
| AI 咨询聚合目录 | 先读缓存，未命中再调各服务 | 任一目录失败用缓存兜底；全部失败 → 500 |

**关键决策**：把高频角色判断从「同步查库」改为「JWT 声明」，把真正同步的跨服务调用收敛到低频的批量查用户名与聚合层，避免下单链路被 user-service 拖累。

## 5. 数据库设计

采用「单 MySQL 实例、多 schema」策略，三个业务服务各持独立 schema（`user_db` / `trade_db` / `life_db`），共享数据库服务器但禁止跨 schema 联表，保留数据库层面的物理隔离，又避免引入多个数据库实例的运维成本。

### 核心订单状态机（外卖）

```
pos=0 待接单 ─骑手接单→ pos=1 骑手已接单 ─商家备餐→ pos=2 商家已出餐
       ─骑手取餐→ pos=3 骑手配送中 ─骑手送达→ pos=4 顾客已取餐 ─用户评价→ pos=5 已评价
```

| 操作 | 角色 | 状态变化 |
| --- | --- | --- |
| 接单 | 骑手 | 0 → 1 |
| 完成备餐 | 商家 | 1 → 2 |
| 已送达 | 骑手 | 2 → 4 |
| 评价 | 用户 | 4 → 5 |

评分字段（菜品评分、配送评分、酒店评分、娱乐评分）均为 `(0, 5]` 的一位小数，平均评分经 SQL 触发器或服务内事务重算，保证订单与评价的一致性。

## 7. 关键技术与设计决策

1. **渐进式微服务化**：保留原页面为 BFF 兼容层，新业务 API 落到三个独立进程，避免现有用例和演示流程中断。
2. **JWT 声明替代同步查库**：高频角色判断本地解析，降低跨服务调用对下单链路的耦合。
3. **同服务事务消除跨服务事件**：把销量统计与订单放在同一服务，省去一整套跨服务写。
4. **单点故障降级**：BFF 聚合层并发调用 + 单点降级，任一服务故障不导致整体 500。
5. **统一健康检查**：每个组件提供 `health/live`（存活）、`health/ready`（就绪，含数据库）、`health/version`（版本）三端点，支撑容器健康检查和 CI 验收。
6. **安全基线**：真实口令不进仓库（未提交的 `.env`），Secret 由部署脚本幂等创建，镜像用提交 SHA + 分支名标签、不使用 `latest`。

## 9. CI/CD 与 DevOps

`.github/workflows/ci.yml` 按五阶段流水线执行，任一阶段失败阻止后续发布或部署：

1. **01 Quality**：格式与静态检查。
2. **02 Test**：在 Ubuntu、Windows、macOS 三平台运行兼容层、UC01–UC09 E2E 回归与三个微服务的全部公开 API 契约测试。
3. **03 Build**：独立构建 BFF / user / trade / lifestyle 四个版本化镜像并推送到 GHCR。
4. **04 Deploy**：创建临时 Kind 集群与三个 schema，部署网关、BFF、三个服务与数据库。
5. **05 Verify**：检查存活、就绪、版本一致性，上传 Kubernetes 日志与资源证据。

镜像同时使用完整 Git 提交 SHA 与分支名作为标签，版本检查不一致时流水线失败；测试报告、Pod 日志、资源快照与健康检查响应均作为 GitHub Actions Artifact 保留。

### 实际排障案例

首次部署流水线在 `Deploy` 阶段三个微服务无法通过启动探针，根因是微服务镜像已安装 `PyMySQL` 但未执行 `pymysql.install_as_MySQLdb()`，导致 Django 使用 MySQL 后端时找不到 `MySQLdb` 模块。修复后在 `services/__init__.py` 注册驱动并为三平台测试增加 MySQL 驱动冒烟检查，随后 18/18 Jobs 全部成功。详见 `02_docs/CI-CD故障排查记录.md`。

## 10. Kubernetes 部署与弹性伸缩

- **清单**：`03_devops/k8s/base` 使用 Kustomize 部署 Nginx 网关、Django BFF、三个业务微服务与 MySQL 8，数据库使用 PVC，四应用镜像由部署脚本替换为同一提交 SHA 的精确版本。
- **自动扩缩容**：`autoscaling.yaml` 为 user/trade/lifestyle 三个业务 Deployment 配置 CPU HPA（1–3 副本，目标 60%），集群先安装 Metrics Server。
- **故障兜底**：网关对业务 upstream 设置 2 秒连接超时、3 秒读写超时，并把 502/504 拦截为 `{"error":"dependency service temporarily unavailable","fallback":true}`（HTTP 503），保证单服务故障只影响对应请求，其他服务健康检查仍成功。
- **回滚**：提供 `rollback-k8s.ps1` / `rollback-k8s.sh` 一键回滚脚本。

故障隔离与 HPA 实验在 Docker Compose、kubeadm 集群中均有实际记录（`04_tests/performance/results/`）。

## 11. 性能对比（单体 vs 微服务）

在**同一 Docker Compose + MySQL 8.0 + gunicorn + nginx** 环境、同一台机器、同一脚本、同一并发参数（120 请求 / 并发 12 / 各 3 次）下对照，结果如下：

| 接口 | 单体吞吐 | 微服务吞吐 | 结论 |
| --- | --- | --- | --- |
| 美食列表 | 28–41 req/s | 230–293 req/s | 微服务约 **7–10× 更快**，主因单体 `sync_food_sales` 的 N+1 缺陷 |
| 酒店列表 | 202–265 req/s | 261–309 req/s | 微服务约 **1.2–1.5× 更快**，JSON 响应更小 |
| 博客列表 | 104–139 req/s | 107–115 req/s | 吞吐接近，微服务因跨服务查用户名略增延迟 |

**内存占用**：微服务在三个接口上均低约 **50–58MB**（JSON 响应远小于 HTML 页面）。

报告遵循「只报实测数字、逐接口解释差异」的原则，未笼统宣称「微服务全面提速」，而是如实区分：美食/酒店吞吐提升来自消除 N+1 与更小的 JSON 契约，博客吞吐接近但内存显著更低。详见 `04_tests/performance/results/performance-comparison-2026-09-03.md`。

## 12. 项目亮点总结

1. **完整的软件工程闭环**：从需求规格、概要/详细设计、用例与追溯表，到实现、三层测试、容器化、CI/CD、K8s 部署与性能验证，覆盖课程全部环节。
2. **工程化的微服务拆分**：以「同服务事务 + JWT 声明 + 单点降级」化解跨服务一致性与耦合难题，而非简单按表拆库。
3. **可验证的质量证据**：114 项测试 + 54 个微服务 API 契约覆盖 + 三平台 CI + Kind 集群部署验收，全部可复现。
4. **诚实的性能结论**：不夸大微服务优势，逐接口归因（N+1、JSON 契约、跨服务调用），体现严谨的工程态度。
5. **健壮的运维能力**：统一健康检查、故障兜底降级、HPA 弹性伸缩、一键回滚与完整的排障记录。
