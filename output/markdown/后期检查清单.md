## 任务 1：把后端拆成至少 3 个业务微服务 ✅

### 1.1 服务划分（3 个业务服务 + 网关/BFF + 数据库）

```
前端/浏览器 ──▶ API 网关 / BFF（路由·鉴权·聚合·限流，非业务服务）
                     ├─▶ user-service       用户与身份服务    schema: user_db   表: User
                     ├─▶ trade-service     交易服务(外卖/团购) schema: trade_db  表: Food/Order/GroupBuyCoupon/Temp
                     └─▶ lifestyle-service 本地生活与内容服务 schema: life_db    表: Hotel/HotelOrder/Play/PlayOrder/Blog/Comment
```

证据：
- 划分图（Mermaid + ASCII）：`02_docs/微服务拆分方案.md`「一、微服务划分图」。
- 代码落地：`01_source/services/{user_service,trade_service,lifestyle_service}/`，每个服务是独立的 Django 进程（独立 `config/settings.py`、`config/urls.py`、`config/wsgi.py`）。
- 划分理由：user 是横切基础能力（账号/角色/认证）；trade 是订单状态机最复杂服务（缺省 `Food` 与 `Order` 同服务，销量同步走同库事务）；lifestyle 合并酒店/娱乐/社区（到店消费、无配送状态机、低频内容互动），三者合并降低运维成本。详见拆分方案「二、三个微服务划分与理由」。

### 1.2 每个服务能单独构建、测试、部署

- 独立构建：`03_devops/services/Dockerfile` 通过 `ARG SERVICE_MODULE` / `ARG SERVICE_PORT` 一个模板构建不同镜像；CI 对 user/trade/lifestyle 三个 job 分别传 `SERVICE_MODULE` 和端口（`.github/workflows/ci.yml`「03 Build」）。
- 独立测试：CI「02 Test」矩阵按 `services.user_service.config.settings`、`services.trade_service.config.settings`、`services.lifestyle_service.config.settings` 分别跑 Django 测试（`01_source/services/common/settings.py` 的 `build_settings` 工厂，各服务独立 app/settings/命名空间）。
- 独立部署：`03_devops/k8s/base/services.yaml` 中 `food-master-user` / `food-master-trade` / `food-master-lifestyle` 三个 Deployment，各自独立的 Service、探针与资源配额。

### 1.3 每张业务表归属明确，其他服务不直连

11 张表全部归属（`02_docs/微服务拆分方案.md`「三、数据表归属表」）：

| 表 | 归属服务 | 跨服务外键处置 |
| --- | --- | --- |
| User | user-service | — |
| Food / Order / GroupBuyCoupon / Temp | trade-service | 跨服务外键降级为裸 ID（`merchant_id`/`user_id`） |
| Hotel / HotelOrder / Play / PlayOrder / Blog / Comment | lifestyle-service | 跨服务外键降级为裸 ID（`merchant_id`/`user_id`/`author_id`） |

### 1.4 同一数据库服务器、不同 schema、不跨 schema 联表

- 同一 MySQL，三个独立库：`03_devops/data/init-microservice-schemas.sh` 创建 `user_db`、`trade_db`、`life_db`，并**只给应用账号授予对应库的权限**（`GRANT ... ON user_db.*` / `trade_db.*` / `life_db.*`），从权限层面禁止跨库直连。
- 各服务 settings 的 `build_settings(...)` 通过 `USER_DB_NAME`/`TRADE_DB_NAME`/`LIFESTYLE_DB_NAME` 指向独立库；`services/{user,trade,lifestyle}_service/config/settings.py` 分别指定 `db_env`。
- 拆分方案中明确规则：**同服务内保留真实外键与联表；跨服务外键一律降级为裸 ID，详情需调对方服务接口解析**。

### 1.5 跨服务数据操作走接口/事件/消息，并说明失败处理

- 跨服务调用实现：`01_source/services/common/client.py` 提供内部 token 的 HTTP 客户端，`resolve_usernames()` 批量调 user-service `/internal/users`；调用失败返回 `None`/`{}`，调用方兜底为「匿名用户」，不阻断主流程。
- 高频角色判断改为 **JWT 声明携带 `user_id`+`usertype`**，服务本地解析，不在下单/评价主链路实时调 user-service（user-service 宕机不影响已有合法 token 请求）。
- BFF 聚合层（`01_source/myapp/bff.py`）用 `ThreadPoolExecutor` **并发**调三个服务，单点失败只影响对应块（`/space`、`/manage`、`/ai-chat` 聚合），不整体 500。
- 失败处理说明表：「五、跨服务调用说明与失败处理」逐条列出（JWT 无效/过期→401；批量查用户名失败→匿名占位；聚合单点降级；AI 目录缓存兜底）。

### 1.6 改造前后两个代码版本

- 通过 git 标签验证：`git tag -l` 存在 **`monolith-start`**（单体基线），`main` 为微服务版本。
- 提交历史：`cc100a2 feat: implement three-service architecture and CI/CD`（微服务落地）、`ee05e78 feat: implement cross-service calls and BFF aggregation layer`（跨服务+BFF）、`f64a105 feat: complete cloud experiments and add Docker preflight`。

## 任务 3：两项云原生实验 ✅

### 3.1 自动扩缩容（HPA + 压测）

- 资源请求/限制与探针：`03_devops/k8s/base/services.yaml` 为每个业务服务配置 `resources.requests`/`resources.limits`（如 trade：requests `50m/96Mi`，limits `500m/384Mi`）+ `startupProbe`/`readinessProbe`/`livenessProbe`。
- HPA：`03_devops/k8s/base/autoscaling.yaml` 三个 HPA，`minReplicas:1`、`maxReplicas:3`、CPU 目标 `60%`，含 scaleUp（无稳定窗口、每 60s 100%）与 scaleDown（稳定窗口 120s、每 60s 50%）。
- 实测记录：`04_tests/performance/results/hpa-kubeadm-2026-08-31.md`
  - 初始：1 副本，CPU `2%/60%`。
  - 持续压测（`/api/trade/foods`，并发 100，120s）：CPU 升到 `846%/60%`→`855%/60%`，Deployment 从 1 → 2 → **3 Ready Pods**。
  - 冷却（等 180s）：CPU 回到 `2%/60%`，缩回 **1 Pod**。
  - 结论：PASS。
- 原始逐批数据：`04_tests/performance/results/hpa-20260831-151545-load-*.json`（18 个批次），均含 `requests/successful/failed/error_rate/throughput_rps/average_ms/p95_ms/status_codes`，如 load-1：2000 请求、吞吐 138.682 rps、平均 641.447ms、P95 700.87ms、错误率 0。
- ⚠️ 环境限制说明（记录中已注明）：前 7 批完成 **14000/14000** 请求成功；后续批次因 **Windows 宿主机压测进程连接容量耗尽**出现 `network_error`，这些原始文件作为环境局限保留，**不作为应用性能结果**。

### 3.2 故障处理（熔断/超时/降级/隔离）

- 实现方式：网关对业务 upstream 设置 **2s 连接超时、3s 读写超时**，并把 502/504 拦截为 503 JSON 兜底（`03_devops/k8s/base/nginx.yaml` 的 `proxy_intercept_errors` + `error_page 502 504 = @service_unavailable`，返回 `{"error":"dependency service temporarily unavailable","fallback":true}`）。
- Compose 实测：`04_tests/performance/results/fault-compose-2026-08-31.md`
  - `docker compose stop trade-service` → 交易接口返回 **HTTP 503 + `fallback:true`**；同一时刻 `user-service`、`lifestyle-service` 健康检查仍为 **HTTP 200**；`start` 后交易接口恢复 200。
- Kubernetes 实测：`04_tests/performance/results/fault-k8s-2026-08-31.md`
  - 临时挂起 HPA、把 `food-master-trade` 缩到 0 → 请求经 BFF/Nginx 返回 **503 fallback**；`user-service`、`lifestyle-service`、BFF readiness 均 **HTTP 200**；恢复后交易健康端点回到 200。
- 结论：单点故障被隔离到对应路由，其他服务不随之崩溃，符合“返回事先设计的兜底结果、其他服务不跟着崩溃”的要求。

## 任务 4：对比改造前后的性能 ✅（已完成 Docker 容器对照）

### 4.1 测试条件（如实记录）

- 版本：单体=`main` 的 BFF/单体兼容层（`web` 服务，单进程全部业务逻辑 + 单库）；微服务=`main` 的 `01_source/services/`（user/trade/lifestyle）。
- 环境：**同一 Docker Compose + MySQL 8.0 + gunicorn + nginx**；同一台 Windows 11；同一份 `04_tests/performance/benchmark.py`。
- 每批负载：120 请求、并发 12、3 次、超时 5s；`--docker-service` 用 `docker stats` 采容器 CPU/内存。
- 网关：单体经 nginx `/` → `web` 容器；微服务经 nginx `/api/*` → user/trade/lifestyle 容器。

### 4.2 接口对照（3 个主要接口，同一环境、各 3 次）

| 接口 | 单体 | 微服务 | 说明 |
| --- | --- | --- | --- |
| 美食列表 `/food/` vs `/api/trade/foods` | 120/120，28–41 req/s，平均 283–407ms，P95 383–442ms，内存 ~130–142MB | 120/120，230–293 req/s，平均 38–49ms，P95 56–64ms，内存 ~80MB | 单体逐菜品做 `sync_food_sales` N+1 聚合写回；微服务只 `filter`+`serialize` |
| 酒店列表 `/hotel/` vs `/api/lifestyle/hotels` | 120/120，202–265 req/s，平均 43–56ms，P95 64–78ms，内存 ~133MB | 120/120，261–309 req/s，平均 36–43ms，P95 55–59ms，内存 ~76MB | 微服务 JSON 更小、略快、内存更低 |
| 博客列表 `/blog/` vs `/api/lifestyle/blogs` | 120/120，104–139 req/s，平均 82–108ms，P95 111–126ms，内存 ~134MB | 120/120，107–115 req/s，平均 98–105ms，P95 117–124ms，内存 ~77MB | 吞吐接近；单体用 DB 外键 join，微服务做一次到 user-service 的 HTTP 解析；微服务内存更低（约 −57MB） |

### 4.3 原始结果文件

- `04_tests/performance/results/monolith-{food,hotel,blog}-2026-09-03.json`（单体 3 次/接口）。
- `04_tests/performance/results/microservice-{trade-foods,lifestyle-hotels,lifestyle-blogs}-2026-09-03.json`（微服务 3 次/接口）。
- `04_tests/performance/results/performance-comparison-2026-09-03.md`（对照报告与差异解释）。

### 4.4 结论

1. 同一 Docker+MySQL+gunicorn+nginx 环境、同一脚本、各 ≥3 次；已记录并发、吞吐、平均/P95、错误率、CPU/内存。
2. 结果**不一致**：美食/酒店微服务更快（约 7–10× / 1.2–1.5×）；博客吞吐接近，但微服务内存更低（约 −57MB）。
3. **未写“微服务全面提速”**；只把实测到的提升（美食/酒店吞吐，及整体内存占用）写入结论，其余如实解释。
